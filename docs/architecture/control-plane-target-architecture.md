# GateWeave 控制面终极架构与演进边界

## 1. 文档状态

本文记录 GateWeave 控制面的目标形态，用于约束第九章及后续迭代的模块边界、领域模型、数据模型和通信方向。

目标形态现在确定，功能仍按教程章节逐步落地。尚未进入当前章节的能力只记录设计，不提前创建空包、占位接口、
数据库表或无调用方代码。

第九章只实现原教程涉及的内容：启动 `gateweave-center`、建立服务与路由的持久化基础、查询路由配置，并验证
HTTP 到数据库的完整链路。

## 2. 不可破坏的架构约束

1. `gateweave-center` 是控制面，负责注册、路由编辑、配置发布、节点管理和管理 API。
2. `gateweave-engine` 是数据面，只执行已经发布的配置，不直接读取控制面的编辑表。
3. `gateweave-center` 与 `gateweave-engine` 不形成 Maven 依赖，二者只通过 `gateweave-contract` 和进程通信协作。
4. `gateweave-spring-boot-starter` 是可选接入方式。非 Java 服务可以直接调用标准 HTTP 注册 API。
5. 服务注册不等于配置发布。注册数据和路由编辑完成后，必须经过校验与发布才能被 Engine 使用。
6. 发布内容是不可变快照。通知只传递分组、版本和校验信息，Engine 收到通知后重新拉取快照。
7. Engine 必须保留最后一个校验成功的版本。Center 暂时不可用或新版本无效时，不清空现有路由。
8. 外部组件只存在于适配器边界。领域层不依赖 Spring、JDBC、MyBatis、HTTP、MQ 或注册发现客户端。

## 3. 终极业务链路

```text
业务应用
  └─ Starter 或标准 HTTP 客户端
       ├─ 注册服务、操作和参数元数据
       ├─ 注册服务实例
       ├─ 周期性心跳
       └─ 应用关闭时注销
                    │
                    ▼
             gateweave-center
       ┌─────────────────────────┐
       │ 服务目录与实例状态       │
       │ 路由、认证和策略编辑     │
       │ 配置校验与版本发布       │
       │ 网关分组与节点管理       │
       │ 变更通知与审计           │
       └─────────────────────────┘
                    │
         发布快照 + 版本变更通知
                    │
                    ▼
             gateweave-engine
       ├─ 启动时拉取最新完整快照
       ├─ 运行时订阅版本变更
       ├─ 校验后原子替换路由表
       └─ 失败时继续使用最后有效版本
```

控制台只操作 Center 的管理 API，不直接操作数据库，也不直接向 Engine 下发配置。

## 4. Center 内部领域边界

### 4.1 服务目录 `catalog`

负责描述可被网关调用的服务能力，包括：

- 服务定义：稳定服务标识、应用名称、协议、命名空间和版本。
- 服务操作：接口名称、方法名称和协议操作标识。
- 操作参数：参数位置、名称和类型。
- 服务实例：实例标识、访问地址、元数据、状态和最后心跳时间。

Starter 注册和控制台手工录入最终都进入同一个应用用例，不允许形成两套服务模型。

### 4.2 路由配置 `routing`

负责描述外部 HTTP 请求如何映射到服务操作，包括：

- 路由标识、路径和 HTTP 方法。
- 所属网关分组。
- 目标服务操作。
- 路由参数名称、顺序和目标类型。
- 身份认证模式。
- 调用超时、协议属性、路由属性和有序策略。

路由编辑模型可以修改；Engine 不能直接消费该模型。

### 4.3 配置发布 `release`

负责把一组通过校验的路由生成不可变快照，包括：

- 按网关分组生成单调递增的版本号。
- 将编辑模型转换为 `gateweave-contract` 中的发布契约。
- 保存完整快照、内容摘要和发布时间。
- 记录创建、发布、失败和回滚状态。
- 支持读取指定版本和最后一个已发布版本。

回滚通过重新发布历史快照形成新版本，不修改已经发布的历史记录。

### 4.4 网关集群 `gateway`

负责管理：

- 网关分组及其环境属性。
- Engine 节点注册、心跳和离线状态。
- 节点当前加载版本和最后成功更新时间。
- 分组与节点之间的归属关系。

节点状态只用于控制面观察和发布决策，不进入单次 HTTP 请求执行链。

### 4.5 变更通知 `subscription`

负责发布配置版本变更事件。领域事件只包含：

- 网关分组标识。
- 新发布版本。
- 快照摘要。
- 事件标识和发生时间。

通知传输可以使用长轮询、SSE、MQ 或其他适配器，但不得改变领域事件和 Engine 拉取快照的语义。
通知允许重复，Engine 必须按版本实现幂等处理。

### 4.6 管理与审计 `administration`

负责为控制台提供服务、路由、节点、发布历史和审计查询。管理 API 只编排对应应用用例，不越过应用层直接访问
Repository。

控制台前端未来可以独立部署，不新增第三套后端领域模型。

## 6. 数据模型边界

表名统一使用 `gw_` 前缀。后续能力通过新增独立表扩展，已经发布的核心标识和关联关系不得随章节变化。

### 6.1 第九章建立的基础表

#### `gw_service`

保存服务定义。核心字段包括服务标识、应用名称、协议、命名空间、版本、状态、修订号和时间戳。

唯一性由稳定的 `service_id` 保证。修订号用于乐观并发控制。

#### `gw_service_operation`

保存服务可以执行的操作。核心字段包括操作标识、服务标识、接口名称、操作名称和状态。

使用 `service_id` 关联服务，禁止把接口和方法信息重复存入每条路由。

#### `gw_service_operation_parameter`

保存服务操作的原始参数元数据。使用 `(operation_id, parameter_index)` 保证参数顺序唯一。

#### `gw_route`

保存可编辑路由。核心字段包括路由标识、网关分组、路径、HTTP 方法、目标操作、认证模式、调用超时、属性、状态、
修订号和时间戳。

至少建立以下约束：

- `route_id` 唯一索引。
- `(gateway_group_id, http_method, path)` 唯一索引。
- `service_operation_id` 普通索引。
- 分页查询使用稳定的 `(id, route_id)` 排序。

第九章只有一个默认分组时仍保存 `gateway_group_id`，避免后续引入网关分组时修改路由身份和唯一索引。

#### `gw_route_parameter`

保存 HTTP 输入到目标操作参数的有序映射。使用 `(route_id, parameter_index)` 保证位置唯一。

路由参数与服务操作参数分表：前者表达网关输入映射，后者表达服务自身元数据，两者不能混为一个字段。

### 6.2 后续迭代新增的独立表

- `gw_service_instance`：服务实例、地址、状态和心跳。
- `gw_route_policy`：路由过滤器或策略的类型、顺序和配置。
- `gw_gateway_group`：网关分组和环境配置。
- `gw_gateway_node`：Engine 节点、心跳和当前配置版本。
- `gw_config_release`：不可变发布快照、版本、摘要和状态。
- `gw_event_outbox`：与发布事务一致提交的待发送事件。
- `gw_operation_audit`：关键管理操作和发布审计。

这些表的增加不要求拆分 Maven 模块，也不改变第九章基础表的职责。

## 7. 发布与订阅原则

### 7.1 编辑数据与运行数据隔离

```text
服务注册/人工编辑
       ↓
服务目录与路由编辑表
       ↓
完整性校验
       ↓
不可变发布快照
       ↓
Engine 拉取并原子生效
```

Engine 只读取发布快照接口，禁止组合查询 Center 的服务、操作和路由编辑表。

### 7.2 通知不携带完整配置

通知仅提示“某分组出现新版本”。完整配置始终通过版本化查询接口获取，以避免：

- 通知体过大。
- 消息乱序导致部分配置覆盖。
- 不同通知适配器产生不同配置语义。
- 消息已发送但数据库事务回滚。

发布事务同时写入发布快照与 Outbox。通知适配器异步投递 Outbox 事件，投递失败可以重试。

### 7.3 Engine 原子切换

Engine 拉取快照后先完成契约校验、重复路由校验和插件可用性校验，再构建新的不可变路由表。只有全部成功后才替换
当前引用；失败时记录原因并继续使用旧版本。

## 8. 目标 API 分类

以下路径只冻结职责，不代表第九章全部实现。

### 8.1 注册 API

- 服务与操作幂等注册。
- 服务实例注册。
- 实例心跳。
- 实例注销。

Starter 和标准 HTTP 客户端共享这些 API。

### 8.2 管理 API

- 服务目录查询。
- 路由新增、修改、启停和分页查询。
- 路由策略管理。
- 配置校验、发布、历史查询和回滚。
- 网关分组、节点和版本状态查询。

### 8.3 Engine 配置 API

- 查询分组的最后发布版本。
- 按版本获取完整配置快照。
- 查询版本摘要。
- 建立版本变更订阅或长轮询。

Engine 配置 API 返回 `gateweave-contract` 中的稳定发布契约，不返回 Center 领域对象或数据库实体。

## 9. 分阶段落地顺序

### 第九章：Center 初始查询闭环

- Center 独立启动。
- 使用迁移脚本建立服务、操作、参数、路由和路由参数基础表。
- 建立 `catalog` 与 `routing` 当前用例需要的领域模型和 Repository 端口。
- 使用持久化适配器批量恢复路由参数，禁止 N+1 查询。
- 提供分页 HTTP 查询接口。
- 完成领域、持久化、Web、架构和启动测试。

### 后续迭代一：Starter 注册闭环

- 元数据采集。
- 幂等注册。
- 实例心跳和注销。
- 标准 HTTP 注册契约。

### 后续迭代二：路由管理与发布

- 管理 API。
- 草稿校验。
- 版本快照与发布历史。
- Outbox 事件。

### 后续迭代三：Engine 配置同步

- 启动全量拉取。
- 版本通知。
- 原子切换。
- 最后有效版本和失败恢复。

### 后续迭代四：集群与控制台

- 网关分组和节点状态。
- 发布观察与审计。
- 控制台前端。

## 10. 防止后续推翻的检查清单

- 新能力是否仍属于现有 Maven 模块，避免按功能随意拆项目。
- 新表是否属于明确聚合，避免把服务、路由、发布和节点重新塞回一张宽表。
- 编辑模型是否与发布快照隔离。
- Center 与 Engine 是否仍只通过契约和进程通信协作。
- Starter 是否保持可选，非 Java 服务是否仍可通过标准协议接入。
- 新通知实现是否只替换适配器，没有改变版本事件语义。
- Repository 是否批量加载关联数据并提供稳定分页。
- 新配置能否向后兼容旧快照，失败时 Engine 能否继续使用最后有效版本。
